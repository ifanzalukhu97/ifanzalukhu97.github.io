# Design Document

## Overview

This design implements the four in-scope findings from the Cloudflare "Is Your Site Agent-Ready?" scan: robots.txt with AI bot rules + Content Signals, an auto-generated sitemap, an Agent Skills Discovery index, and WebMCP tool exposure. Everything is static output from the existing Jekyll build — no server, no new runtime, no new hosting.

## Architecture

```
ifanzalukhu97.github.io/
├── robots.txt                          # NEW — static, plain text
├── _config.yml                         # MODIFIED — add jekyll-sitemap plugin + include .well-known
├── Gemfile                             # MODIFIED — add jekyll-sitemap gem
├── .well-known/
│   └── agent-skills/
│       ├── index.json                  # NEW — Agent Skills Discovery index
│       ├── profile/SKILL.md            # NEW
│       ├── articles/SKILL.md           # NEW
│       └── talks/SKILL.md              # NEW
├── _layouts/default.html               # MODIFIED — append WebMCP registration script
└── _site/sitemap.xml                   # GENERATED by jekyll-sitemap at build time (not committed)
```

Nothing here touches `index.html` section markup, CSS design system, or the dev.to fetch logic — all "Things to Preserve" from the structure steering remain intact.

## Components and Interfaces

### 1. `robots.txt` (site root, static file)

**Validates: Requirements 1.1, 1.2, 1.3, 1.4, 1.5, 1.6**

Plain static file at repo root. Jekyll copies root-level static files to `_site/` unchanged (no front matter needed, no Liquid processing required for a `.txt` file with no front matter — it's just copied byte-for-byte). Served as `text/plain` by GitHub Pages automatically based on extension.

Structure:
```
User-agent: *
Allow: /
Content-Signal: ai-train=yes, search=yes, ai-input=yes

User-agent: GPTBot
Allow: /

User-agent: OAI-SearchBot
Allow: /

User-agent: ChatGPT-User
Allow: /

User-agent: Claude-Web
Allow: /

User-agent: anthropic-ai
Allow: /

User-agent: Google-Extended
Allow: /

User-agent: Amazonbot
Allow: /

User-agent: Bytespider
Allow: /

User-agent: CCBot
Allow: /

User-agent: Applebot-Extended
Allow: /

Sitemap: https://www.ifanzalukhu97.com/sitemap.xml
```

**Note on Cloudflare interaction**: Cloudflare's managed-robots.txt feature detects whether the origin already serves a valid robots.txt (HTTP 200). Once this file is live, Cloudflare should stop replacing it. If Cloudflare is configured to *prepend* its own managed block regardless, that block will not conflict since it uses the same `User-agent: *` / `Content-Signal` syntax — but this is verified by fetching the live URL post-deploy, not by anything in this repo.

### 2. Sitemap via `jekyll-sitemap`

**Validates: Requirements 2.1, 2.2, 2.3, 2.4**

Add to `Gemfile`:
```ruby
gem "jekyll-sitemap"
```

Add to `_config.yml`:
```yaml
plugins:
  - jekyll-sitemap
```

`jekyll-sitemap` walks `site.pages`, `site.posts`, and `site.collections` (with `output: true`) and emits `sitemap.xml` + `sitemap.xsl` into `_site/`. Because the workflow (`pages.yml`) runs `bundle exec jekyll build` directly rather than the `github-pages` gem, there is no plugin whitelist restriction — this differs from a vanilla `github-pages` gem setup and is why this plugin works here without extra CI changes.

**Slide deck pages caveat**: `slides/*.html` files have no YAML front matter (confirmed: they start directly with `<!DOCTYPE html>`), so Jekyll treats them as static files, not "pages" — `jekyll-sitemap` only includes Jekyll pages/posts/collections with front matter, not arbitrary static files. To get the two slide URLs into the sitemap without adding front matter to self-contained slide decks (which would break their standalone nature per the "Slides are independent" architecture decision), the sitemap will list them via a small **custom sitemap addition** rather than relying on jekyll-sitemap to auto-discover them:

- Simplest compliant option: keep `jekyll-sitemap` for the homepage, and rely on the `_slides` collection metadata (`_slides/*.md`, which already has front matter with `url` and `date`) to be picked up. But `_slides` has `output: false`, so `jekyll-sitemap` won't emit entries for a collection that produces no output pages either.
- **Decision**: Override `jekyll-sitemap`'s output with a small custom `sitemap.xml` template (a Jekyll page with front matter `permalink: /sitemap.xml`) that loops over `site.slides` (using the existing `url`/`date` front matter fields already used in `index.html`) plus the homepage. This avoids adding a second gem/plugin dependency conflict and keeps the sitemap accurate without needing front matter on the slide HTML files themselves.
- This means the `jekyll-sitemap` gem is **not needed** — a single Liquid-templated `sitemap.xml` page is simpler, has zero new dependencies, and directly reuses `site.slides` the same way `index.html` already does. (Lazy/YAGNI: don't add a gem when 15 lines of Liquid do the job with less moving parts.)

Revised plan: no new gem. Create `sitemap.xml` at repo root as a Jekyll-processed page:

```liquid
---
layout: null
permalink: /sitemap.xml
---
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>{{ site.url }}/</loc>
  </url>
  {% for slide in site.slides %}
  <url>
    <loc>{{ site.url }}{{ slide.url }}</loc>
    <lastmod>{{ slide.date | date_to_xmlschema }}</lastmod>
  </url>
  {% endfor %}
</urlset>
```

`layout: null` prevents the default layout (with all the HTML head/CSS) from wrapping the XML output.

### 3. Agent Skills Discovery Index

**Validates: Requirements 3.1, 3.2, 3.3, 3.4**

`.well-known/` is dot-prefixed, which Jekyll excludes by default. Add to `_config.yml`:
```yaml
include:
  - .well-known
```

`.well-known/agent-skills/index.json` (static JSON, no Liquid needed — values are stable):
```json
{
  "$schema": "https://schemas.agentskills.io/discovery/0.2.0/schema.json",
  "skills": [
    {
      "name": "profile",
      "type": "skill-md",
      "description": "Retrieve Ifan Zalukhu's professional profile: role, expertise, and links.",
      "url": "https://www.ifanzalukhu97.com/.well-known/agent-skills/profile/SKILL.md",
      "digest": "sha256:<computed>"
    },
    {
      "name": "articles",
      "type": "skill-md",
      "description": "Find Ifan Zalukhu's latest technical articles on .NET, AWS, and AI.",
      "url": "https://www.ifanzalukhu97.com/.well-known/agent-skills/articles/SKILL.md",
      "digest": "sha256:<computed>"
    },
    {
      "name": "talks",
      "type": "skill-md",
      "description": "List Ifan Zalukhu's conference talks and slide decks.",
      "url": "https://www.ifanzalukhu97.com/.well-known/agent-skills/talks/SKILL.md",
      "digest": "sha256:<computed>"
    }
  ]
}
```

Each `SKILL.md` is a short static markdown file describing, in plain language, where an agent finds the data (e.g. "fetch `https://www.ifanzalukhu97.com/llms.txt` for a structured profile summary" and "fetch `https://dev.to/api/articles?username=ifanzalukhu97&per_page=4` for latest articles"). This deliberately points to data sources that already exist (`llms.txt`, the dev.to API) rather than inventing new endpoints — satisfies the "truthful, no invented capability" acceptance criterion.

`digest` values are computed once at authoring time with `shasum -a 256 <file>` and hardcoded into `index.json`. This is a manual step, documented as a maintenance note (ponytail: fixed digest with manual update, no build-time hashing — acceptable ceiling for 3 static files that rarely change; upgrade path is a tiny Rake task if the file count grows).

### 4. WebMCP Tool Registration

**Validates: Requirements 4.1, 4.2, 4.3, 4.4, 4.5**

Appended to the existing inline `<script>` block at the end of `_layouts/default.html`, after the dev.to fetch IIFE. Runs on page load, feature-detected:

```javascript
(function () {
  if (!(navigator.modelContext && typeof navigator.modelContext.registerTool === 'function')) return;

  var PROFILE = {
    name: "Ifan Jaya Suswanto Zalukhu",
    title: "Head of Engineering, SimpliDOTS",
    tagline: "Senior C# .NET Backend Engineer, AWS Community Builder (AI Engineering)",
    links: {
      linkedin: "https://linkedin.com/in/ifanzalukhu97",
      github: "https://github.com/ifanzalukhu97",
      devto: "https://dev.to/ifanzalukhu97"
    }
  };

  var TALKS = [
    {% for slide in site.slides %}
    { title: {{ slide.title | jsonify }}, event: {{ slide.event | jsonify }}, date: {{ slide.date | date_to_xmlschema | jsonify }}, url: {{ slide.url | jsonify }} }{% unless forloop.last %},{% endunless %}
    {% endfor %}
  ];

  navigator.modelContext.registerTool({
    name: "get_profile",
    description: "Get Ifan Zalukhu's professional profile summary and key links.",
    inputSchema: { type: "object", properties: {} },
    execute: function () { return PROFILE; }
  });

  navigator.modelContext.registerTool({
    name: "list_talks",
    description: "List conference talks and slide decks by Ifan Zalukhu.",
    inputSchema: { type: "object", properties: {} },
    execute: function () { return TALKS; }
  });

  navigator.modelContext.registerTool({
    name: "list_recent_articles",
    description: "List Ifan Zalukhu's most recent dev.to articles.",
    inputSchema: { type: "object", properties: {} },
    execute: function () {
      return fetch('https://dev.to/api/articles?username=ifanzalukhu97&per_page=4')
        .then(function (r) { return r.ok ? r.json() : []; })
        .catch(function () { return []; });
    }
  });
})();
```

`TALKS` is rendered server-side via Liquid (reusing `site.slides`, same source as the "Recent slides" section) so it needs no extra fetch. `list_recent_articles` reuses the same public dev.to endpoint already called by the existing fallback-safe fetch — no new network dependency, no write/mutating capability exposed (satisfies Requirement 4's read-only constraint).

Wrapped in an IIFE with an early-return feature check, so browsers without `navigator.modelContext` (i.e. virtually all of them today) execute one `if` and stop — no errors, no measurable cost.

## Data Models

### robots.txt (plain text, RFC 9309 + Content Signals draft)
No schema — line-based directives as shown above.

### sitemap.xml (sitemaps.org protocol)
```
<urlset><url><loc/><lastmod/></url>...</urlset>
```

### Agent Skills index.json (Agent Skills Discovery RFC v0.2.0)
```typescript
interface SkillsIndex {
  $schema: "https://schemas.agentskills.io/discovery/0.2.0/schema.json";
  skills: Array<{
    name: string;        // lowercase alphanumeric + hyphens
    type: "skill-md";
    description: string;
    url: string;
    digest: string;      // "sha256:{hex}"
  }>;
}
```

### WebMCP Tool Definition
```typescript
interface WebMCPTool {
  name: string;
  description: string;
  inputSchema: object;  // JSON Schema
  execute: () => any | Promise<any>;
}
```

## Correctness Properties

### Property 1: robots.txt Validity
WHEN any crawler requests `/robots.txt` THEN it receives HTTP 200, `Content-Type: text/plain`, containing at least one `User-agent` directive and a `Sitemap:` line.
**Validates: Requirements 1.1, 1.2, 1.5**

### Property 2: Sitemap Completeness
WHEN `/sitemap.xml` is fetched THEN it is valid XML and contains a `<loc>` entry for the homepage and for every entry currently in `site.slides`.
**Validates: Requirements 2.1, 2.2**

### Property 3: Agent Skills Index Integrity
WHEN `/.well-known/agent-skills/index.json` is fetched THEN each `skills[].digest` matches the SHA-256 of the content actually served at `skills[].url` at time of publish.
**Validates: Requirements 3.1, 3.2**

### Property 4: WebMCP Non-Interference
WHEN the page loads in a browser without `navigator.modelContext` THEN no JavaScript error is thrown and no visible/behavioral change occurs on the page.
**Validates: Requirements 4.1, 4.4**

### Property 5: No Invented Capabilities
WHEN a SKILL.md file or WebMCP tool describes a data source THEN that data source (URL/endpoint) actually exists and returns real data (llms.txt, dev.to API, site.slides) — nothing points to a non-existent API.
**Validates: Requirements 3.3, 3.4, 4.2**

## Error Handling

| Scenario | Handling |
|---|---|
| `navigator.modelContext` absent (nearly all current browsers) | Early `return` in IIFE, no-op |
| `list_recent_articles` dev.to fetch fails | `.catch()` returns empty array, matches existing fallback pattern used by the visible articles section |
| Cloudflare still prepends managed robots.txt content after this file is deployed | Documented as a post-deploy manual check against the live URL; not something the repo can control |
| `.well-known` accidentally excluded again by a future `_config.yml` edit | Sitemap/skills 404 — caught by the manual verification step in tasks.md |

## Testing Strategy

| Test | How |
|---|---|
| Jekyll build succeeds | `bundle exec jekyll build`, check for errors |
| robots.txt served correctly | `curl -I` after build/deploy, confirm 200 + text/plain locally via `_site/robots.txt` |
| sitemap.xml valid & complete | Open `_site/sitemap.xml`, confirm entries for homepage + 2 slides |
| `.well-known` present in `_site/` | `ls _site/.well-known/agent-skills/` after build |
| SHA-256 digests correct | `shasum -a 256` each SKILL.md, compare to `index.json` |
| WebMCP feature detection safe | Load page in current desktop browser (no `navigator.modelContext`), confirm no console errors |
| No regression to existing sections | Visual diff of homepage before/after; dev.to fetch still works |
